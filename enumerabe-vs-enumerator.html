The idea

A book and a bookmark

Mentor

Think of a book and a bookmark. The book holds the pages but has no idea which page anyone is reading. The bookmark knows exactly one thing: where this reader is. Two people can read the same book at once, each with their own bookmark, without disturbing each other.

In .NET the book is IEnumerable<T> and the bookmark is IEnumerator<T>. The only thing a book can do in this analogy is hand out a fresh bookmark, and that is its single method, GetEnumerator().

IEnumerable<T>: the sequence

Microsoft describes it as the interface that exposes the enumerator. It has exactly one method to implement, GetEnumerator(), which returns an IEnumerator<T>. It holds no position.

IEnumerator<T>: the cursor

It supports a simple iteration over a generic collection. It holds the position and has Current, MoveNext(), Reset() and Dispose().

One sentence to remember: you foreach over an enumerable; the enumerator is what does the walking.

    Chapter 1 · one sequence, many cursors

    Hand out bookmarks and move them independently

    Mentor

    Every call to GetEnumerator() creates a new cursor that starts before the first element. Moving one cursor never moves another. That is why two nested foreach loops over the same list work: each loop asked for its own enumerator.

    Create up to three enumerators over the same playlist

    var playlist = new Playlist { "Intro", "Verse", "Chorus", "Outro" };   // IEnumerable<string>

      Docs: a new enumerator is positioned before the first element, and Current is undefined there, so MoveNext must be called before reading Current. The enumerator has no exclusive access to the collection.

        Chapter 3 · the cursor's life

        Before, on, after: what each call returns

        Mentor

        A cursor is a little state machine. Most exam questions about enumerators are really questions about these states: what does MoveNext() return here, is Current valid there, what happens if the list changes in the middle. This simulator follows the documented behaviour of List<T>'s enumerator.

        Drive a List<string> enumerator by hand

        var list = new List<string> { "A", "B", "C" };
IEnumerator<string> e = list.GetEnumerator();
          The rules this simulator follows, from the docs
          • Initially the enumerator is before the first element; Current is undefined there.
          • Current returns the same object until MoveNext is called; MoveNext sets Current to the next element.
          • Past the end, MoveNext returns false, and keeps returning false. Current is undefined there too.
          • For List<T>: if the collection is changed, the enumerator is irrecoverably invalidated and the next MoveNext or Reset throws InvalidOperationException.
          • Reset exists for COM interoperability. List<T>'s enumerator implements it explicitly, so you need a cast to the non-generic IEnumerator to call it. Other enumerators may simply throw NotSupportedException.

          "Undefined" means you must not rely on the value. The simulator shows what you'd typically see, but don't write code that depends on it.

          Chapter 4 · anatomy

          Which member belongs to which interface?

          Mentor

          When you implement these by hand, the hardest part is keeping straight which member goes on which class. The sequence class gets the GetEnumerator methods. The cursor class gets everything to do with position. Both generic interfaces also drag in their older non-generic parents, which is where the "explicit" members come from. Sort these and read the explanations.

          Sort the members

          Pick a side for each member.

          Why there are two Current properties

          Microsoft's notes to implementers: MoveNext() and Reset() don't depend on T and appear only on the non-generic interface. Current appears on both with different return types. Implement the non-generic Current as an explicit interface implementation.

          Why there are two GetEnumerator methods

          IEnumerable<T> derives from the non-generic IEnumerable, so both methods are required. Microsoft's samples implement the non-generic one explicitly and have it call the generic one, to avoid a naming conflict.

          Chapter 5 · the heart of a hand-written cursor

          Spot the correct MoveNext

          Mentor

          A hand-written enumerator over an array usually keeps an index field. Because a fresh enumerator sits before the first element, the index starts at -1, and MoveNext advances it and reports whether it's still inside the array.           Chapter 6 · let the compiler write the cursor
          
  
          yield return: an enumerator without a cursor class
          
  
          Mentor
    
          Writing a cursor class by hand is good for understanding, and sometimes a task asks for it. In everyday code you write an
    iterator instead: a method with yield return. The compiler generates the Current, MoveNext and
    Dispose for you. The surprising part is when the method body runs. Step through Microsoft's own example and watch the two sides take turns.
          
  
          
  
          
    
          Who runs when?
          
    
          
    
          
      
          Caller
          
      
          Iterator method
          
    
          
    
          
    
          
    
            
  
            
  
            Docs: calling an iterator doesn't execute it immediately. When iteration starts, it runs until the first yield return, then is suspended and the
  caller gets the value. Each later iteration resumes after that yield return. Iteration completes at the end of the method or at yield break.
  The return type of an iterator can be IEnumerable, IEnumerable<T>, IEnumerator or IEnumerator<T>
  (or the async variant). A return statement is a compile-time error inside an iterator block.
            

            



            
  
            Pitfalls
            
  
            Things that trip people up
            
  
            Changing the collection inside foreach

            var list = new List<string> { "A", "B" };
foreach (var s in list)
{
    list.Add(s + "!");      // next MoveNext throws InvalidOperationException
}
            
    
            For List<T>, any add, change or delete invalidates the enumerator, and its next MoveNext or Reset throws. The interface docs
    describe the general case as undefined behaviour, so a hand-written enumerator may not throw; it may just give wrong results.
            
  
            Reading Current before the first MoveNext, or after the last
    
            Both positions have an undefined Current. Microsoft's sample enumerators throw InvalidOperationException there; List<T>'s enumerator does not
    promise anything. Always check MoveNext()'s result first.
            
  
            Expecting an enumerator to start over
    
            Once MoveNext has returned false, you can't set Current to the first element again with the generic interface; create a new enumerator instead.
    Reset may not be implemented. In practice: call GetEnumerator() again, or just foreach again.
            
  
            Forgetting Dispose in a manual loop
    
            IEnumerator<T> inherits IDisposable. foreach disposes the enumerator for you in a finally; a manual while (e.MoveNext())
    loop should do the same, most simply with using var e = sequence.GetEnumerator();.
            
  
            foreach over null
    
            Applying foreach to null throws NullReferenceException. An empty collection is fine: the body just doesn't run.
            
  
            Thinking an iterator ran when you called it

            var songs = LoadSongs();    // nothing inside LoadSongs has run yet
foreach (var s in songs) { } // now it runs, one yield at a time
            
    
            Side effects like logging, validation or exceptions inside an iterator happen during enumeration, not at the call.
            
  
            Where yield is not allowed
    
            Not in methods with in, ref or out parameters, not in lambdas or anonymous methods, and not in catch or finally blocks
    or in a try that has a catch. A try with only a finally is fine.
