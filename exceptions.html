The idea

An exception is an object that travels up the call stack

Mentor

When something goes wrong deep inside a method, that method usually can't decide what to do about it. A file helper doesn't know whether a missing file should show an error dialog, retry, or crash the request. So instead of returning an error code that every caller has to check, it throws an object describing the problem. That object travels back up the chain of callers until one of them says "I know how to handle this".

Along the way it carries a record of where it came from: the stack trace. Most of the subtle rules in this page are really about protecting that record.

throw: start the journey

Exceptions are created by using the throw keyword, and they're objects whose types all ultimately derive from System.Exception.

try / catch / finally: meet it

try marks code that might fail, catch handles a failure when that's reasonable, and finally cleans up resources afterwards.

One sentence to remember: the stack trace begins where the exception is thrown and ends where it's caught, and every rule about rethrowing exists to keep the beginning of that list intact.

Chapter 1 · propagation

Who catches it, and which finally blocks run on the way?

Mentor

The runtime looks for a matching catch starting in the method that threw, then in its caller, then in that method's caller, and so on. The first compatible handler wins; control continues after that catch, and the methods in between never resume. Microsoft also notes that before the catch block runs, the runtime runs the finally blocks in between. Configure each method and press Throw.

    Chapter 2 · catch order

    First match wins, so specific goes first

    Mentor

    A try can have several catch clauses. The runtime checks them top to bottom and runs at most one. Because exception types form an inheritance hierarchy, a clause for a base type also matches every derived type. Put a general clause above a specific one and the specific one could never run, so the compiler refuses. Rearrange the clauses and see.

    Chapter 3 · finally

    The block that always runs

    Mentor

    Cleanup code has a problem: if you put it at the end of the try, an exception skips it; if you copy it into every catch, sooner or later one copy gets out of date. finally runs whether the try succeeded, failed and was caught, failed and wasn't caught here, or even returned early.       Docs: a finally block runs last, after the try and any matched catch, and always runs, whether or not an exception is thrown or a matching catch is found. A try needs at least one catch or a finally; a bare try is a compile error. In practice, using statements are the usual way to get a finally that disposes something.

      Chapter 4 · the stack trace

      Mentor

      Chapter 5 · exception filters

      catch … when: decide before catching

      Mentor

      A common anti-pattern is catching an exception, inspecting it, and doing throw; if it wasn't the one you wanted. An exception filter does the inspection before catching: if the condition is false, the clause simply doesn't match and the search continues. Microsoft points out that the filter is evaluated before the stack is unwound, so the original call stack and local variables are still intact, and a false filter leaves the stack trace untouched.

      Microsoft's file example: which clause runs?

      The logging trick, and its rule 
      catch (Exception e) when (LogException(e))   // LogException always returns false
{
}

      Microsoft shows a filter that logs and returns false: the exception is recorded with its full stack while the clause never actually catches it. The rule that comes with filters: don't throw from them. An exception inside a filter is swallowed and the filter counts as false, which is very hard to debug. Try the checkbox above.

        Guidelines
        
  
        The rules Microsoft spells out
        
  
        When to use exceptions at all
    
          
      
        • Throwing or handling an exception costs significant resources and time, so throw only for truly extraordinary conditions, not for predictable events or flow control.
          • 
      
        • Don't throw an exception if user input is invalid: users will occasionally type nonsense, so offer a retry instead. For parsing, that's the TryParse pattern.
          • 
      
        • Don't throw when a return code is sufficient, and don't routinely catch an exception, ignore it and carry on.
          • 
    
        
  
        Catching
    
          
      
        • Don't catch an exception unless you can handle it and leave the application in a known state.
          • 
      
        • If you catch System.Exception, rethrow it with throw at the end of the catch block. Avoid catching it at all except in top-level handlers.
          • 
      
        • Callers should be able to assume there are no side effects when a method throws: restore state, like undoing the withdrawal when a transfer's deposit fails.
          • 
      
        • Don't log the same exception at every level as it's rethrown; it clutters logs, and the exception already carries its stack trace.
          • 
    
        
  
        Throwing
    
          
      
        • Prefer the most specific predefined type, and set ParamName on argument exceptions. The nameof(age) in your Task 6 does exactly that.
          • 
      
        • Use static throw helpers where they exist, such as ArgumentNullException.ThrowIfNull.
          • 
      
        • Don't raise exceptions in finally clauses or from exception filters.
          • 
      
        • In async methods, validate arguments before the asynchronous part. Exceptions thrown later are stored in the task and only surface when it's awaited.
          • 
      
        • In iterators, an exception only reaches the caller when the iterator advances to that point.
          •
