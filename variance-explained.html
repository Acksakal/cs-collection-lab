Covariance and contravariance, example by example

Each chapter takes one example from the Microsoft page, states the problem a working developer had, and lets you poke at it. Words with a dotted underline have a definition: hover, tap or focus them.

The page calls its classes Base and Derived. Here Base is Shape and Derived is Circle, with Square as a second derived class so we can show what goes wrong.

Shapebase class Circle: Shape Square: Shape Coin: Circle

The problem

A Circle is a Shape. Is a box of Circles a box of Shapes?

Mentor

You already rely on polymorphism daily: a method that wants a Shape happily takes a Circle. The trouble starts when the type is wrapped in a generic. Is a List<Circle> acceptable where a List<Shape> is wanted? What about an Action<Circle>? The answer isn't the same for every generic type, and variance is the set of rules that decides it.

Everything on this page follows from one question: does the generic type hand values out, take values in, or both?

out: values come out of it

A Circle coming out can always be treated as a Shape. So a source of circles can stand in for a source of shapes. That is covariance: the conversion runs the same way as Circle → Shape.

in: values go into it

Something that accepts any Shape can certainly accept a Circle. So a consumer of shapes can stand in for a consumer of circles. That is contravariance: the conversion runs the opposite way.

A type that does both, like List<T> with its Add and its indexer, gets neither. It is invariant, which is the default for every type parameter.

Example 1 · covariance

Passing a List<Circle> to a method that reads shapes

The page's PrintBases(IEnumerable<Base>) example.

Mentor

I wrote a helper that prints any sequence of shapes. You have a List<Circle> and want to print it. Before C# 4 that call didn't compile, and people copied the list into a new List<Shape> just to make the compiler happy. All my method does is read. Reading circles as shapes can't hurt anyone, so the language should allow it.

static void PrintShapes(IEnumerable<Shape> shapes)
{
    foreach (Shape s in shapes) Console.WriteLine(s);
}

List<Circle> circles = new() { new Circle(1), new Circle(2), new Circle(3) };
PrintShapes(circles);                       // compiles: no cast, no copy
IEnumerable<Shape> shapes = circles;        // same conversion, as an assignment

Reading is safe. Writing is where it breaks.

seen asShape

PrintShapes(IEnumerable<Shape>)

    Press the first button to see why reading is harmless, then the second to see what the compiler is protecting you from.

    If you write the API

    Ask for the weakest thing you need. A method that only loops should take IEnumerable<Shape>, not List<Shape>. Because IEnumerable<out T> is covariant, callers with a list of any derived type can use it.

    If you call the API

    You pass your List<Circle> directly. Nothing is copied and nothing is cast: the method receives your list, viewed through an interface that only lets it read.

    Why it's safe: in IEnumerable<T> the T appears only in output positions. There is no Add(T) to misuse, so the trick in the second button can't even be written.

    Example 2 · contravariance

    Reusing a general callback where a specific one is wanted

    The page's Action<Base> assigned to Action<Derived>.

    Mentor

    Some API asks you for an Action<Circle>: "give me something to run for each circle". You already have a logger that works on any Shape. It feels backwards to hand a shape-handler to something asking for a circle-handler, but think about who supplies the argument. The API will only ever pass circles, and your logger copes with every shape. The page's own words for this are that it "seems backward" yet is type-safe.

    Action<Shape> log = s => Console.WriteLine(s.GetType().Name);
Action<Circle> onCircle = log;      // compiles: contravariance
onCircle(new Circle(1));            // log receives a Circle, which is a Shape

    If you write the API

    You declare the callback with in: delegate void Action<in T>(T obj). Your promise is "I will only pass a T in; I never get one back". That promise is what makes general handlers acceptable.

    If you call the API

    You write one handler for the base type and reuse it for every derived type's event or callback, instead of one wrapper lambda per type.

    Example 3 · contravariant interface

    One comparer for every kind of shape

    The page's ShapeAreaComparer passed to SortedSet<Circle>.

    Mentor

    I want sets of circles sorted by area, and later sets of squares sorted by area. Area is defined on Shape, so the comparison logic is identical. Without contravariance I'd need CircleAreaComparer, SquareAreaComparer and so on, each a copy of the same three lines. IComparer<in T> lets one comparer written for Shape serve them all.

    class ShapeAreaComparer : IComparer<Shape>
{
    public int Compare(Shape? a, Shape? b)
    {
        if (a == null) return b == null ? 0 : -1;        // nulls sort first
        return b == null ? 1 : a.Area.CompareTo(b.Area);
    }
}

// The constructor wants IComparer<Circle>. We give it an IComparer<Shape>.
var byArea = new SortedSet<Circle>(new ShapeAreaComparer())
    { new Circle(7.2), new Circle(100), null, new Circle(.01) };

    Fill the set and watch the comparer work

    Collection
    The same ShapeAreaComparer object is used whichever collection you choose.

    If you write the API

    SortedSet<T>'s author asks for IComparer<T> and never thinks about base classes. The in on the interface does the work: a comparer only receives values, so one for a less derived type is always good enough.

    If you call the API

    You write the comparer once against the type that owns the property you compare, here Shape.Area, and pass it to collections of any derived type.

    Example 4 · both at once

    Func<in T, out TResult>: narrow the input, widen the output

    The page's Func<Base, Derived> assigned to three other Func types.

    Mentor

    A Func has a parameter and a return value, so both rules apply to the same delegate, each to its own type parameter. Suppose I have a method that takes any Shape and returns a Circle. Any code that will only ever pass circles in, or is satisfied with getting some Shape back, can use it as is.

    static Circle MyMethod(Shape s) => s as Circle ?? new Circle(1);

Func<Shape, Circle>  f1 = MyMethod;
Func<Shape, Shape>   f2 = f1;    // return type widened      (out)
Func<Circle, Circle> f3 = f1;    // parameter type narrowed  (in)
Func<Circle, Shape>  f4 = f1;    // both

    Assignment checker: click a type to change it

    Func<, > source = MyMethod;
    Func<, > target = source;

    The rule to memorise: a conversion is allowed when the target's parameter is the same or more derived, and the target's return type is the same or less derived.

    Example 5 · two different mechanisms

    Binding a method, then converting the delegate

    The page's Type1, Type2, Type3 example. Here: Shape ← Circle ← Coin.

    Mentor

    Two separate features can relax types, and this example chains them. The first has existed since C# 2: when you create a delegate from a method group, the method's signature doesn't have to match exactly. The second is the generic variance from the earlier chapters, added in C# 4, which converts one delegate object to another delegate type.

    static Coin MyMethod(Shape s) => s as Coin ?? new Coin();

Func<Circle, Circle> f1 = MyMethod;   // step 1: method binding
Func<Coin, Shape>    f2 = f1;         // step 2: generic variance
Shape result = f2(new Coin());

    Follow the two types along the inheritance ladder

    The limit worth knowing: step 2 only works between types built from the same generic type definition, here Func<T, TResult>. Two delegate types you declared yourself with identical signatures do not convert to each other.

    Example 6 · the author's side

    Declaring your own variant interface

    Mentor

    When you design a generic interface, you choose. Marking a type parameter out or in gives your callers the conversions from the chapters above, and in exchange the compiler holds you to the matching restriction. Flip the keyword and watch which members it rejects.

    Be the API author

    Variance keyword

    Rules for out T

    Allowed as a method's return type and a read-only property's type. Not allowed as a method parameter. The page also notes it can't be used as a generic constraint on the interface's methods.

    Rules for in T

    Allowed as a method parameter type, and as a generic constraint on the interface's methods. Not allowed as a return type.

    The exception to the rules · arrays

    Array covariance: the old, unchecked kind

    Based on the C# language specification (§17.6, §12.24.2) and the C# programming guide.

    Mentor

    Everything so far was checked by the compiler: if a conversion could ever let a wrong type in, it was rejected. Arrays are the one place where C# lets the dangerous conversion through anyway. Arrays have been covariant since the first version of .NET, long before generics and out/in existed, and the behaviour was kept for compatibility. Microsoft's programming guide says it plainly: converting an array of a more derived type to an array of a less derived type is allowed, but this operation is not type safe.

    // The specification's own example
string[] sa = new string[10];
object[] oa = sa;               // compiles: array covariance
oa[0] = null;                   // OK
oa[1] = "Hello";                // OK
oa[2] = new ArrayList();        // ArrayTypeMismatchException at run time

    Store into a covariant array

    Shape[] shapes = circles; // circles is really a Circle[3]

    Store into shapes[i]

    What the compiler sees

    Shape[] shapes

    Any Shape looks storable, so every button compiles.

    What the object really is

    Circle[]

    Every store compiles. The runtime checks each one against the array's actual element type, Circle.

    In a nutshell

    • What it is. For two reference types A and B, if a reference conversion exists from A to B, the same conversion exists from A[] to B[]. So a Circle[] can be used as a Shape[], and a string[] as an object[].
    • Why it is unsafe. Arrays allow writing, and the conversion only changes how the array is viewed, not what it really is. A variable typed Shape[] may point to a Circle[].
    • How .NET protects you. Every assignment to an element of a reference-type array includes a run-time check that the value is null or compatible with the array's actual element type. If not, ArrayTypeMismatchException is thrown. The error surfaces when the program runs, not when it compiles.
    • Not for value types. Array covariance does not apply to arrays of value types: an int[] cannot be treated as an object[]. That line is a compile error.

    What to be careful about

    Methods that write into an array parameter

    A method taking object[] may receive a string[]. The specification's example is a Fill method that writes a value into each element: it works for matching arrays and throws ArrayTypeMismatchException on the first write when a boxed int is stored into a string[].

    static void Fill(object[] array, object value)
{
    for (int i = 0; i < array.Length; i++) array[i] = value;
}

Fill(new string[3], "x");   // fine
Fill(new string[3], 1);     // compiles, then ArrayTypeMismatchException

    If your method only reads, ask for IEnumerable<T> or IReadOnlyList<T>. Their covariance is checked at compile time and they have no setter to misuse.

    Passing an array element by ref

    Passing an element of a reference-type array as a ref or out argument triggers a run-time check that the array's element type is identical to the parameter type. In the specification's example, F(ref b[1]) throws because b is declared object[] but really holds a string[].

    static void F(ref object x) { }

object[] a = new object[10];
object[] b = new string[10];
F(ref a[0]);   // OK
F(ref b[1]);   // ArrayTypeMismatchException
    Converting a covariant array to Span<T>

    A Span<T> allows writing, so creating one over a covariant array throws ArrayTypeMismatchException. Microsoft lists this as a breaking change in C# 14: a Span<T> overload may now be chosen where C# 13 picked an IEnumerable<T> overload, and that call can crash with a covariant array. The documented workarounds are calling .AsEnumerable() or offering a ReadOnlySpan<T> overload.

    string[] s = { "a" };
object[] o = s;              // array variance

C.R(o);                      // C# 14: picks R(Span<T>), crashes in the Span constructor
C.R(o.AsEnumerable());       // workaround

    If you write the API

    Don't take T[] just to read it. A parameter typed IReadOnlyList<T> or IEnumerable<T> gives callers the same flexibility with compile-time safety. If you must write into an array you were given, remember it may be an array of a more derived type.

    If you call the API

    Prefer passing an array whose declared type matches its real type. If an ArrayTypeMismatchException appears, look for a place where a derived array was assigned to a base-typed variable or parameter.

    Limits

    Where variance stops

    Only interfaces and delegates can be variant

    Classes and structs are always invariant. List<Circle> is never a List<Shape>; it converts to IEnumerable<Shape> because of the interface, not the class.

    Only reference types take part

    With a value type as the type argument, the parameter behaves as invariant.

    IEnumerable<object> a = new List<string>();   // fine: string is a reference type
IEnumerable<object> b = new List<int>();      // error: int is a value type

    An int would need boxing to become an object, and a variance conversion never changes the data, only how it's viewed.

    Delegates combine only when their types match exactly

    Variance lets you assign an Action<Shape> to an Action<Circle> variable. It does not let you combine the two into one multicast delegate, even though calling both with a circle would be safe.

    A type parameter can be one or the other, never both

    An interface can have several type parameters with different variance, as Func<in T, out TResult> does. A single parameter that is both read and written must stay invariant.

    Covariant return types are a different feature

    Since C# 9, an overriding method may return a more derived type than the method it overrides. The name is similar, but it concerns inheritance between classes, not conversions between generic types.
